1. 背景与目标

开发者往往同时拥有多个 LLM 供应商、多个 API 分组和多个 Agent 应用。模型名称、协议、密钥位置和失败表现不一致，导致切换成本高、故障难定位、客户端配置重复。

产品目标：用户在 RelayDeck 本地维护供应商、公共模型和路由；Agent 应用只连接稳定本地入口，从而安全、可恢复、可观察地使用多个模型。

成功结果

用户可在一个界面建立上游、映射公共模型、发布路由、配置 Agent，并在失败时判断是网关、网络、认证、模型还是客户端配置问题。

衡量信号

新增 API 到可测试模型的路径明确；同步与发布有反馈；任何自动修改均可预览和恢复；客户端无需保存供应商密钥。

2. 目标用户

用户主要问题期望结果
个人开发者想以较低成本切换模型，又不想反复改 API Key。在常用 Agent 中选公共模型，供应商变更不影响日常使用。
重度 Agent 用户同时用 Codex、Claude Code、OpenCode，配置格式不同。在 RelayDeck 中预览、应用和恢复各 Agent 配置。
小团队维护者多个供应商/API 分组难以维护优先级和可用性。同一公共模型可配置多个上游，并查看健康、额度、成本和测试结果。

3. 产品范围与非目标

范围产品承诺状态
本地多供应商管理维护供应商、API 分组、原始模型、公共模型与绑定。现有
本地统一网关为 OpenAI 与 Anthropic 兼容客户端提供稳定本地入口。现有
模型路由维护发布状态、优先级和可配置的回退链。现有
Agent 配置辅助面向已适配应用提供检测、预览、备份、应用与恢复。现有/扩展中
自动模型分类同步后做初步分类；未能可靠确认时进入未分类，允许人工调整。持续优化

非目标

  • 不托管或上传用户密钥，不把本地调用转交 RelayDeck 云端。
  • 不承诺任意第三方模型都支持视觉、流式、工具调用或某一 Agent 的原生特性。
  • 不在未经用户确认时覆盖外部 Agent 配置或系统环境变量。
  • 不把“模型系列”当作上游协议的强制判断依据。

4. 关键用户旅程

J-01 新增供应商并使用模型

  1. 用户新增供应商和 API 分组，填写协议、地址与密钥来源。
  2. 用户执行网络测试并同步模型列表，看到成功、失败或未分类结果。
  3. 用户创建或选择公共模型，将原始模型绑定为上游并设置优先级。
  4. 用户置顶并发布公共模型，随后在对应 Agent 中刷新/同步配置并实际测试。

J-02 为 Agent 应用切换到 RelayDeck

  1. 用户在“配置到对应 Agent 应用”查看应用检测结果与当前配置来源。
  2. 用户打开详情，查看当前配置、计划替换、密钥引用方式和将保留的内容。
  3. 用户创建备份并应用；系统告知成功/失败和是否需重启 Agent。
  4. 若效果不符合预期，用户从同一位置恢复指定备份。

J-03 排查调用失败

  1. 用户从概览或路由详情看到异常状态。
  2. 用户区分管理台、网关、网络测试、对话测试和客户端配置的失败来源。
  3. 用户依据错误分类修复认证、网络、模型绑定或 Agent 配置，再进行定向重试。

5. 核心能力：自动接入 Agent 与模型配置

RelayDeck 的关键价值不仅是提供本地网关，更是让用户把已发布公共模型快速、安全地接入实际使用的 Agent。用户不应手动查找每个应用的配置目录、协议字段、模型目录和密钥位置。

自动接入完成定义：用户选择一个已发布模型与一个目标 Agent 后，RelayDeck 自动生成候选配置，写入本地网关地址和安全的密钥引用，同步可发现模型或快捷槽位；用户在写入前可预览、校验、备份，写入后可恢复。

5.1 支持等级与当前应用目录

支持等级应用用户获得的能力当前状态
完整自动配置Codex、OpenCode、Claude Code检测、配置预览、备份、写入、恢复、RelayDeck 网关地址与模型目录/别名同步。已支持
仅检测/说明WorkBuddy（CodeBuddy CLI）、百度搭子 DuMate显示本机检测、官方入口与能力说明；不写入网关或模型配置。不自动配置
待验证候选Claude Agent Teams、OpenClaude、Grok、GitHub Copilot、MiMo Code、Aider、Goose、Gemini、Cline、Continue、Cursor、Kilo、Kiro、Qwen Code、OpenClaw 等已登记 Agent统一列表中显示检测结果与候选协议；只有官方配置格式、外部网关能力和回滚路径验证通过后，才能升级为完整自动配置。待适配

5.2 自动化行为边界

  • 只同步 RelayDeck 中已发布的公共模型；未发布模型不能被写入客户端可选目录。
  • Codex 使用模型目录与可管理槽位；Claude Code 使用可编辑的 Claude 型别名；OpenCode 写入完整已发布模型列表。
  • 密钥只以安全引用或本地受保护配置方式接入，页面、备份摘要和日志均不显示密钥值。
  • 检测到应用不等于已安全适配。未验证应用必须显示“仅检测/说明”，不能提供会误导用户的“自动配置”按钮。

7. 优先级与可见交互要求

优先级事项完成定义
P0自动化 Agent 模型接入三个完整适配 Agent 可在一次确认操作后使用 RelayDeck 已发布模型；同步流程具备预览、验证、单次备份、写后校验与恢复。
P0同步、自动分类与绑定可信度每个同步结果能解释为何已绑定、待映射或未分类，不把发现到的模型误报成已成功绑定。
P0服务状态与错误反馈所有耗时操作都有即时反馈；管理台与各网关状态独立且一致。
P0Agent 配置恢复性预览、备份、应用、恢复可重复验证，且不泄露/覆盖无关配置。
P1OpenCode 快捷别名在完整已发布模型列表之外，提供可选的逻辑别名，不遮蔽真实模型名。
P1严格主备路由用户能够配置并验证何时必须按优先级、何时重试、何时回退和何时停止。

7. 产品验收标准

  • 用户可以从一个新 API 完成同步、分类确认、公共模型绑定、发布并在目标 Agent 中使用。
  • 用户在同步、测试、发布、应用配置时能看到准确的开始、进行中、成功或失败反馈。
  • 未发布公共模型仍可在管理视图中维护；已发布列表只包含符合发布条件的模型。
  • 自动修改 Agent 配置前可查看差异，完成后可选择正确备份恢复。
  • 界面始终区分网络检查与真实对话测试、服务存在与服务就绪、草稿与已发布状态。
  • 用户可明确知道某个应用是否支持自动配置；不支持项不提供误导性的应用入口。

8. 需要产品确认的事项

以下事项会改变用户可见行为或配置风险，应在进入实现前明确确认。
  • 是否为 OpenCode 增加可选快捷别名层，以及别名是否出现在其模型选择器中。
  • 是否把优先级升级为严格主备路由，以及哪些错误可触发回退。
  • 新增 Agent 是否支持自动配置、仅说明，还是完全不出现。
  • 桌面端是否需要正式安装包、自动更新和多平台真实设备验收。
